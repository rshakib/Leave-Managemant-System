# Build Plan — Leave Management System

The project is split into small phases. Each phase is built **and tested on its own** before moving
on, and lists what it **depends on**. Backend and its React screens are built together in each phase,
so every phase ends with something you can actually click and try.

**How to read this:** do the phases in order. If a phase's dependency isn't finished, it won't work yet.

## Phase 0 — Project skeleton & local environment

- **Depends on:** nothing.
- **Build:** `backend/` FastAPI app with a `/health` route; `frontend/` Vite + React app;
  `docker-compose.yml` running PostgreSQL; `.env.example`; `README.md`; `git init`.
- **Done when:** the backend returns HTTP 200 on `/health`, the frontend dev page loads, and
  `docker compose up` starts PostgreSQL.

## Phase 1 — Database foundation

- **Depends on:** Phase 0.
- **Build:** SQLModel models and a shared base class carrying common `created_at`, `updated_at`,
  `created_by` fields; async `AsyncSession` setup; a `models/__init__.py` that re-exports every
  `table=True` model; Alembic init and the first autogenerated migration; a DB-backed health check.
- **Done when:** `alembic upgrade head` creates the base tables and `/health/db` succeeds.

## Phase 2 — Organisation structure (divisions, departments)

- **Depends on:** Phase 1.
- **Build:** `division` and `department` SQLModel tables (with a multi-column `UniqueConstraint` in
  `__table_args__`) and an admin CRUD API. Uniqueness rules: division name unique; department name
  unique within its division. A division/department with active employees can only be deactivated,
  never deleted. Include thin Pydantic-only `Create`/`Read` models derived from the table models.
- **Done when:** an admin (via `/docs` for now) can create, edit, list, and deactivate divisions and
  departments, and the uniqueness/deactivate rules reject bad input.

## Phase 3 — Employees

- **Depends on:** Phase 2.
- **Build:** `employee` model (unique code and email, optional supervisor self-reference, `is_active`)
  and an `employee_role` join table; CRUD API; guards that stop an employee being their own supervisor
  or creating a circular supervisor chain; deactivation rules (revoke login, block new submissions,
  keep history).
- **Done when:** employees can be created/edited/deactivated with their division, department, roles,
  and supervisor, and invalid supervisor links are rejected.

## Phase 4 — Authentication & RBAC

- **Depends on:** Phase 3.
- **Build:** password hashing (argon2); JWT login and refresh; a `current_user` dependency; role
  guards (`ADMIN`, `EMPLOYEE`, `APPROVER`); an admin seed command; and auth added to the Phase 2–3
  endpoints so only admins can change configuration.
- **Done when:** you can log in and receive a token, protected endpoints reject unauthenticated
  requests, and role guards block non-admins from admin routes.

## Phase 5 — Frontend shell

- **Depends on:** Phase 4.
- **Build:** routing, an auth context, token handling, an Axios API client, an app layout, a login
  page, protected routes, and the first admin list screen (e.g. divisions). This becomes the template
  every later phase reuses.
- **Done when:** you can log in through the browser, see your role-appropriate landing page, and the
  first list screen loads data from the API.

## Phase 6 — Leave years & leave types

- **Depends on:** Phase 1, Phase 4.
- **Build:** `leave_year` (only one active at a time) and `leave_type`, including the `accrual_mode`
  field the schema was missing (see DECISIONS **D-03**); CRUD API and admin screens.
- **Done when:** an admin can manage leave years and leave types, and the "one active year" rule is enforced.

## Phase 7 — Leave-type assignment & balances

- **Depends on:** Phase 3, Phase 6.
- **Build:** `employee_leave_type` and `leave_balance` (with a computed `available = allocated +
  carried_forward − used − pending`); single and bulk assignment with upsert; balance-row creation on
  assignment; a "my balances" screen for employees.
- **Done when:** an admin can assign leave types (individually or in bulk) and an employee sees correct
  available balances.

## Phase 8 — Weekends, holidays & day-calculation engine

- **Depends on:** Phase 3, Phase 6.
- **Build:** `weekend_setting` (a global default plus per-employee overrides; store `days_of_week` with
  a PostgreSQL `ARRAY`/`JSONB` via `sa_column`); `holiday` with CSV bulk import; and the **pure
  function** `calculate_chargeable_days(employee, start, end, day_type)` covered by focused unit tests.
  Add a calendar-preview UI showing weekends and holidays.
- **Done when:** the day-calculation function passes unit tests for weekdays, weekends, holidays, and
  half-days, and the preview shows the right chargeable days.

## Phase 9 — Approver assignment

- **Depends on:** Phase 3, Phase 4.
- **Build:** `employee_approver` (with a self-approval `CHECK` constraint via `__table_args__`);
  pre-fill the reporting supervisor as an approver; admin can add/remove approvers; blocks that stop an
  employee being their own approver; and the interaction with employee deactivation (see **D-16**).
- **Done when:** an admin can assign one or more approvers to an employee and self-approval is rejected.

## Phase 10 — Leave request submission

- **Depends on:** Phase 7, Phase 8, Phase 9.
- **Build:** `leave_request` and `leave_request_approval` tables; all six FR-LR-2 validations; reserve
  the chargeable days in `pending` inside a single transaction; cross-year splitting (see **D-05**);
  and a request form with live day/balance preview.
- **Done when:** a valid request creates the request plus one pending approval per approver and
  reserves the balance; every validation rule blocks its bad case with a clear message.

## Phase 11 — Approval workflow

- **Depends on:** Phase 10.
- **Build:** approve/reject endpoints; the all-must-approve rule (approve → `APPROVED` and move
  `pending` to `used`); reject → `REJECTED` and release `pending`; mark remaining approvals `SKIPPED`;
  and row-locking so simultaneous approvers can't double-process. Add the approver inbox UI.
- **Done when:** a request only becomes `APPROVED` when every approver approves, a rejection releases
  the balance, and concurrent approvals are handled correctly.

## Phase 12 — Cancellation

- **Depends on:** Phase 11.
- **Build:** employee cancels their own `PENDING` request (releases `pending`); admin cancels an
  `APPROVED` request (restores `used`, proportionally if the leave spanned two years — see **D-31**).
- **Done when:** an employee can cancel only their own pending request, and an admin can cancel an
  approved one with the balance restored.

## Phase 13 — Email notifications & outbox queue

- **Depends on:** Phase 10, Phase 11, Phase 12.
- **Build:** a durable `email_outbox` table plus a background worker with retry and attempt logging;
  the six emails from FR-NOT-1; the pending-approval reminder job (see **D-18**). Development uses a
  console/file email backend.
- **Done when:** every listed event produces a queued email, failures retry and are logged, and the
  reminder job finds overdue approvers.

## Phase 14 — Reporting & CSV export

- **Depends on:** Phase 7, Phase 10, Phase 11.
- **Build:** filtered balance and history queries (by division, department, employee, leave type,
  status, date range) and CSV export (NFR-4). Present the results as tables in the UI.
- **Done when:** an admin can filter the reports and download a CSV that matches the filters.

## Phase 15 — Year-end closing & carry-forward

- **Depends on:** Phase 6, Phase 7.
- **Build:** `leave_carry_forward` log table; the closing action that transfers
  `min(available, max_carry_forward_days)` into the next year's `carried_forward` and writes a log row;
  refuse to close a year that still has pending requests (see **D-15**).
- **Done when:** running the closing action moves the correct days, logs them, and is blocked while
  pending requests exist.

## Phase 16A — Audit log

- **Depends on:** every phase that changes data (2, 3, 6, 7, 8, 9, 10, 11, 12, 14, 15).
- **Build:** the `audit_log` table (append-only, protected by a database trigger) and the recording
  helper; one audit row per business action, written inside the caller's transaction (NFR-1, D-23, D-24);
  the ADMIN-only read API and screen; and a coverage test that every write route is audited or has a
  stated reason not to be.
- **Done when:** each audited action leaves exactly one row with the right actor, entity, action and
  old/new values; failed actions leave none; nobody can update, delete or truncate the log.

## Phase 16B — Balance adjustment screen + closed-year cancellation

- **Depends on:** Phase 16A.
- **Build:** an ADMIN screen and endpoint to adjust one employee's leave balance by hand (required reason,
  an append-only ledger row AND an audit row, D-155…D-159); both reconcile invariants learned about
  adjustments (D-156); `touches_closed_year` on the request detail (D-160). Since **D-153** a request can
  only be cancelled while PENDING, so this is also the only way to repair a wrongly approved request.
- **Done when:** an admin can repair a balance, the ledger and the audit log both show it, and both reconcile
  functions stay clean.

## Phase 16C — Security hardening

- **Depends on:** Phase 16A.
- **Build:** refresh tokens plus the httpOnly cookie (finishing the D-12 amendment), a login rate limit,
  and login auditing (successful and failed attempts) through the same audit log.
- **Done when:** sessions can be refreshed and revoked, repeated password guesses are slowed down, and
  login attempts are recorded.

## Phase 16D-1 — Retention job, health/readiness, CI, golden-path test

- **Depends on:** Phases 16A, 16B, 16C.
- **Build:** the data-retention job (prune only `login_attempt`, unusable `refresh_token` rows and SENT
  `email_outbox` rows, in batches, dry-run by default, once a day in the worker behind an advisory lock);
  `GET /health` (liveness) and `GET /health/ready` (database + migration revision + stale email, with no
  sensitive details); a GitHub Actions workflow (backend, frontend, integration, hygiene) plus weekly
  dependabot; and a marker-selected golden-path integration test with a hard safety guard.
- **Done when:** `pytest -q` stays green and skips the integration marker, the workflow is valid and runs the
  same commands locally, and the retention dry run reports the same counts as the audited apply run.

## Phase 16D-2 — S3 storage, Dockerfiles, nginx + CSP, prod env template

- **Depends on:** Phase 16D-1.
- **Build:** attachment storage behind the existing interface (S3-compatible), Dockerfiles for backend and
  frontend, an nginx config with a Content-Security-Policy, and a filled-in production `.env` template
  (including `TRUSTED_PROXY_COUNT`).
- **Done when:** the containers build and serve the app with a CSP header.

## Phase 16D-3 — The real deployment

- **Depends on:** Phase 16D-2.
- **Build:** the actual deployment, done together with the user step by step: real SMTP, TLS, the email worker
  as its own process, and the first production smoke test.
- **Done when:** the deployed app is reachable, sends real mail and passes the smoke test.

---

## Rules while building

- Finish and test a phase before starting the next one.
- The day-calculation engine (Phase 8) and the balance/approval transactions (Phase 10–11) deserve the
  most tests — they are where correctness matters most.
- Keep the requirements file and this plan as the source of truth; if code and docs disagree, flag it.
